# Security

This document describes the threat model and security controls for the
Hanik improvement loop in this repository. It is written for both human
maintainers and any automated agent operating on this repository.

## Design principles

- **No secrets in state or reports.** `state/state.json` and `reports/*.html`
  contain only criteria names, numeric scores, static recommendation text,
  and timestamps. Nothing derived from environment variables, tokens, or
  external services is ever written to these files.
- **Offline by default.** `src/hanik_loop.py` makes no network calls and
  calls no LLM provider. This removes prompt injection, data exfiltration,
  and unpredictable third-party output as attack surfaces for the loop
  itself. If a future iteration adds an LLM or external tool call, it must
  first extend this document with its own threat model before being
  enabled in the default workflow.
- **Least privilege.** The workflow requests only the GitHub permissions it
  needs (`contents: write`, `pull-requests: write`) and nothing broader
  (no `admin`, no org-wide scopes).

## Prompt and data injection

- All content that could conceivably originate outside this repository's
  trusted history (e.g. `state/state.json`, which is repository-controlled
  but still treated as untrusted input in code) is passed through
  `html.escape()` before being embedded in generated HTML reports. See
  `render_html_report()` in `src/hanik_loop.py` and the corresponding tests
  in `tests/test_hanik_loop.py::test_html_report_escapes_untrusted_state_content`.
- If a future iteration integrates an LLM, all model output must be
  treated as untrusted: it must never be interpolated into shell commands,
  file paths, or executed directly, and must be escaped the same way state
  content is escaped today.
- The loop never parses or executes recommendation text; it is inert,
  human-readable strings only.

## Secrets

- No API keys, tokens, or credentials are hard-coded anywhere in this
  repository.
- The only credential used by the automated dispatch path is
  `HANIK_DISPATCH_TOKEN`, a **separate, minimally-scoped** GitHub token
  (fine-grained personal access token or a dedicated GitHub App
  installation token) stored as a repository secret. It must be scoped to
  `repository_dispatch` (or the narrowest permission that allows it) on
  this repository only, and must not be the same token used for anything
  else.
- The default `GITHUB_TOKEN` provided automatically by GitHub Actions is
  intentionally **not** used to trigger the next iteration. GitHub
  disables workflow-to-workflow recursion when events are generated by the
  built-in `GITHUB_TOKEN` specifically to prevent runaway loops; using a
  separate `HANIK_DISPATCH_TOKEN` is a deliberate choice, not an
  oversight, and is documented so a future maintainer does not "fix" it by
  switching back to `GITHUB_TOKEN` and accidentally defeating the
  recursion guard together with the other controls below.

## Untrusted MCP servers and least privilege

Any use of Model Context Protocol (MCP) servers in tooling connected to
this repository (for example, GitHub's own MCP server or Microsoft's
[`microsoft/mcp`](https://github.com/microsoft/mcp) tooling) must follow
these rules:

- **Explicit allowlist only.** MCP servers are never enabled by default or
  auto-discovered. Each server must be explicitly named, reviewed, and
  added to an allowlist before it can be used against this repository.
  Arbitrary or third-party MCP servers must never be enabled implicitly.
- **Least privilege per server.** Each allowed MCP server should be
  granted only the scopes/tools it needs (e.g. read-only file access)
  rather than broad repository or organization admin access.
- **Secure HTTP transport authorization.** Per the official MCP
  authorization specification, MCP servers exposed over HTTP act as OAuth
  2.1 **resource servers**, not token issuers:
  - Clients must use the OAuth 2.1 Authorization Code flow with PKCE;
    the deprecated Implicit and Resource Owner Password flows must not be
    used.
  - Servers must publish Protected Resource Metadata (RFC 9728) and
    respond with `401` + `WWW-Authenticate` when unauthenticated, so
    clients can discover the correct authorization server.
  - Access tokens must be validated for both signature/expiry and
    **audience** (RFC 8707 Resource Indicators), so a token minted for one
    MCP server can never be replayed against a different one.
  - Redirect URIs must be exact matches; wildcards are not permitted.
  - STDIO-transport MCP servers (no network exposure) should use OS-level
    credential handling and are out of scope for the HTTP OAuth profile
    above, but still fall under the allowlist and least-privilege rules.
- This repository does **not** enable any MCP server by default as part of
  the automated loop; `src/hanik_loop.py` does not depend on or call any
  MCP server. Any future MCP integration must be added to an explicit
  allowlist and documented here before being wired into the workflow.

## Cost and rate controls

- The loop is entirely local (pure Python, standard library only) and
  performs no network calls, so it has no external API cost.
- The workflow (`.github/workflows/hanik-loop.yml`) sets a job-level
  `timeout-minutes` so a hung or misbehaving run cannot consume runner
  minutes indefinitely.
- `HANIK_BATCH_SIZE` bounds the number of iterations in each workflow run
  (default `50`); the workflow advances the per-batch maximum from the
  persisted state before starting each batch.
- `concurrency` is configured in the workflow so overlapping runs on the
  same ref cancel or queue rather than running in parallel and racing on
  `state/state.json`.

## Retention

- `reports/` accumulates one HTML file per iteration under version control,
  giving a permanent, auditable history. Because iterations are bounded by
  `HANIK_MAX_ITERATIONS`, the number of files is bounded too.
- `state/state.json` retains a `history` array of all past iterations.
  Pruning/archival strategies for very long histories are a documented
  hypothesis in `HANIK_SPEC.md`, not yet implemented.
- No personal data is ever retained (see `HANIK_SPEC.md` §5 Privacy).

## Emergency shutdown

To stop the loop immediately:

1. Do not re-run or approve the `workflow_dispatch` / `repository_dispatch`
   trigger. The loop never schedules itself; it only runs when explicitly
   invoked.
2. Set the repository variable/secret `HANIK_CONTINUOUS` to `false` (or
   delete it). The workflow will not perform the completion-triggered
   dispatch to the next iteration unless this is explicitly `true`.
3. Revoke or delete the `HANIK_DISPATCH_TOKEN` repository secret. Without
   it, the dispatch step that requests the next iteration cannot
   authenticate.
4. If a run is currently in progress, cancel it from the Actions tab (this
   is also covered by the workflow's `concurrency` group, which lets a new
   dispatch supersede/cancel an in-flight one if configured to do so).

## Why ordinary `GITHUB_TOKEN` recursion is restricted (and why that's fine)

GitHub Actions intentionally does not trigger new workflow runs from
events (like `push` or `repository_dispatch`) generated using the default
`GITHUB_TOKEN`. This is a built-in guard against accidental infinite
workflow loops. This repository's design works *with* that guard rather
than around it: the completion-triggered dispatch step uses the separate
`HANIK_DISPATCH_TOKEN` secret specifically so it can chain forward when
`HANIK_CONTINUOUS=true`, while still being independently revocable,
independently scoped, and never used for anything except that one
`repository_dispatch` call. This is a deliberate, minimal-privilege
design decision, not an attempt to bypass GitHub's anti-recursion
protections for unrelated purposes.
